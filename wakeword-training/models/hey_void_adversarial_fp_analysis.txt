- openwakeword.data.generate_adversarial_texts() (the function that produced the adversarial phrase list) draws from the GLOBAL np.random state with no seed argument, and generate_negative.py never seeds that global state before calling it - so even the exact SET of ~15 generated phrases used for this dataset cannot be deterministically reproduced by re-running the generator against the same config.
- Augmentation type (orig/aug0/aug1) and raw-vs-augmented lineage ARE recoverable via the filename suffix convention, and are reported below.

FUTURE IMPROVEMENT (not implemented - recommendation only)
------------------------------------------------------------------------------
filename -> phrase:      generate_negative.py's TTS-generation loops (adversarial and neutral-speech) already know, at generation time, which phrase index/text produced each output file (tts_backends.py's generate() iterates 'texts[i % len(texts)]' per sample) - this could be written to a sidecar manifest (e.g. a <category>_manifest.jsonl with {filename, phrase} per line) with a small, additive change to SapiSampleGenerator.generate() / PiperSampleGenerator.generate() and their callers, at negligible cost.

filename -> voice:       Similarly, _voice_tokens()/the resolved voice per sample index is already computed inside generate() and could be recorded per file in the same manifest.

filename -> aug source:  augment_directory() already derives its output filenames deterministically from the source raw file's stem ('{stem}_orig.wav', '{stem}_aug{v}.wav'), so raw-to-augmented traceability already exists structurally via the filename suffix convention - this part does not need a new manifest, only the raw-file-to-phrase/voice manifest above, which the augmented filename stem would then transitively inherit.
