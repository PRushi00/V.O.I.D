ROOT CAUSE ASSESSMENT
==============================================================================
Classification: E - Combination of data/training-capacity limitation and evaluation-data limitation

[Rank 1] Confidence: high (directly supported by per-sample data)
  False positives are heavily concentrated in the adversarial category: 27/29 (93%) of all FPs, an 18% FP rate within that category (27/150) versus 0% for noise (0/150) and 2.7% for speech (2/75). Many of these are high-confidence (mean score 0.79, median 0.85) and threshold-resistant: 24/27 remain false positives at the runtime threshold of 0.6, and 18/27 remain false positives even at 0.7. This indicates the model has not learned a robust acoustic-phonetic boundary between "hey void" and its deliberately-close adversarial phrases (e.g. "hey voice", "okay void") - consistent with the dev-scale model/data size this config explicitly documents as a proof-of-pipeline configuration, not a production one.

[Rank 2] Confidence: medium (distinct, data-supported pattern, separate from the FP finding)
  All 9 false negatives are augmented variants (aug0/aug1); zero are unaugmented (_orig) clips, out of 150 positive validation clips split evenly 50/50/50 across orig/aug0/aug1. This suggests the augmentation pipeline (pitch shift, noise, distortion, reverb, bandstop) is pushing some positive examples into misclassification, and/or that the model has not been given enough capacity or positive-source diversity to remain robust across the augmentation range on top of the current 2-voice positive set.

[Rank 3] Confidence: low-to-medium (confirmed structural fact, but NOT empirically attributable to specific false positives with current data)
  generate_negative.py never passes a voices= argument to get_tts_backend(), and get_tts_backend defaults voices=None -> a single default SAPI voice for ALL adversarial-phrase and neutral-speech negative clips, even though positive generation now cycles ["David","Zira"]. This is a verified asymmetry re-checked in the current source. It is a PLAUSIBLE contributing factor (a single monotone negative voice could share more incidental acoustic similarity with the now-more-varied positive set than a diverse negative voice set would), but per-file voice cannot be recovered from the current dataset (no filename->voice manifest exists), so this cannot be confirmed as a direct cause of the specific 29 false positives - reported as a hypothesis only, per instructions.

[Rank 4] Confidence: contextual limitation, not a cause
  The validation set is small and entirely synthetic (375 negative clips, ~0.21 hours) - the training pipeline's own evaluate.py caveats already flag this as not representative of real-world robustness. This does not explain the observed 93% adversarial-category concentration, but it does mean the measured 7.73% overall false-accept rate should not be extrapolated to real-world behavior in either direction.

[Rank 5] Confidence: ruled out as primary factor (data-supported)
  Threshold tuning alone does not resolve the core issue: even at threshold 0.9 (well above the runtime 0.6), 10 false positives remain, and 18/27 adversarial false positives persist at 0.7. Raising the threshold trades recall for a modest FP reduction but does not address the underlying phonetic-discrimination gap.

[Rank 6] Confidence: checked, no correlation found
  RMS energy (FP mean 3732.6 vs non-FP-negative mean 3762.4) and clip duration (FP mean 1.86s vs 2.08s) show no meaningful difference between false positives and true negatives. Augmentation type is also evenly distributed among false positives (aug0=10, aug1=11, orig=8, roughly matching the 125/125/125 base rate) - augmentation type does NOT correlate with false positives (in contrast to the false-negative pattern above, which is strongly augmentation-linked).
